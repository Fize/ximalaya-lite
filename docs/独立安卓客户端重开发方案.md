# 喜马拉雅独立 Android 客户端重开发方案

初稿：2026-11-04；方案修订：2026-11-06；阶段3实施记录：2026-11-10。原设计基线保留，阶段3实际结果见第12节及 `history/客户端历史记录.md`。

面向有 Android 开发经验的读者，基于已分析的 `9.4.74.3` APK、SO 逆向和精简候选运行证据。目标是重新开发一个体积可控、没有广告和自动推广的客户端，以核心节目收听和官方账号体系为主；直播与非广告任务处于最低优先级。支付、充值、礼物打赏全部排除，离线下载暂不纳入。

以下“本轮只交付方案”“未来工作”等语句保留初稿语境，不能用作当前工程状态；当前实施结果以阶段记录为准。初稿修订时只更新方案文档、不实施客户端、不修改原包或账号状态。修改前副本位于 `/private/tmp/shixi-plan-before-20261106.md`；回滚本轮修订需恢复该副本，不能删除整份原有方案。

## 1. 推荐路线与决策边界

**推荐独立 Android 应用，自己维护界面、播放服务和本地数据；复用已验证的业务协议，并将必要的签名、地址解析与 JNI 能力隔离到小范围兼容层。** 新应用使用自己的 applicationId 和长期签名，可与官方 App 共存。精简候选保留为对照样本。

重写的主要收益来自：只实现明确需要的页面与业务，不引入广告聚合、营销调度、完整 RN 容器、全量图片/动画资源和无关 SDK。原包删改只减小约 1.81%，不能据此评价独立开发的体积上限。

**用户已确认：“复用协议与必要加密能力，客户端重写”。** 因此复用范围为原 App 的业务接口、官方登录协议及确有必要的签名/解密能力；界面、播放服务与本地存储重新开发。原客户端 Java/Kotlin、RN、播放器等组件组合不构成必须沿用的要求，按本文的功能与体积目标独立选型。

**本轮已确认约束：** 优先采用 Android 当前推荐方案；借鉴 Apple 播客 UI 布局，以 Material Design 3（MD3）实现，可延续喜马拉雅主色；直播和非核心收听能力降至最低优先级；支付、充值、礼物打赏全部排除，离线下载暂不做。

本文面向用户本人及 Android 开发者。具体库、页面组织、设备下限、预算和工期标记为**设计建议**；已有实验为**已观察**；独立应用协议兼容和运行能力为**待验证**。建议用于评审，不将其写成已经完成的实现。

明确区分三件事：

1. **官方账号登录**：身份由喜马拉雅服务端签发、校验；新 App 负责正确处理官方登录流程和会话。
2. **官方发行身份**：自己的包名和签名不会成为原官方发行包，不能把“兼容官方账号”写成“官方签名”。
3. **内容权益**：使用服务端返回的账号权益、试听权限。移除广告/会员推广不改变内容是否获授权。

## 2. 已有证据与尚未证明的能力

证据分为“已观察”“设计建议”“待验证”，下文沿用这三个标记。

| 项目 | 当前已观察 | 对重开发的实际含义 |
|---|---|---|
| 原包和精简候选 | 匿名首页、搜索、播放、暂停、后台播放、恢复和断网处理通过 | 证明原框架中的调用链能工作；独立 App 仍须重新验证 |
| 请求层 | 已定位搜索、专辑、播放、Passport、历史和订阅等路径与构参 | 可以编写协议适配层，不必移植整个 CommonRequestM |
| 主加密库 | `libencrypt.so` 同时承担业务密码能力和证书/DEX 完整性检查 | 不是复制一个 SO 加上 wrapper 就能完成独立移植 |
| 登录库 | RSA 字段转换在自己的无网络测试包中成功，密文解码128字节、重复输出随机 | 只证明字段转换；完整 signature、设备材料和服务端登录接受仍未知 |
| 直播库 | 合成入房签名稳定；Course/ASR key 根据传入包名字符串分支返回 | 不是实际入房或拉流成功；包名相关分支必须先解决兼容性 |
| 媒体转换库 | 合成1024字节数据加解密回环成功 | 证明特定转换函数可调用，不代表全部离线格式可播 |
| 登录、任务 | 有静态调用与模型证据，没有真实账号运行验证 | 不能给“全部兼容”的承诺，必须安排后续独立验收 |
| 直播 | 有房间模型、FLV 字段和 IM 签名调用链，没有实际房间观看证据 | 仅在最低优先级阶段验证，不阻塞核心收听 |

详细证据：[原静态报告](history/喜马拉雅APK逆向分析报告.md)、[SO排查与离线验证](排查与自建方案.md)、[精简候选验收](history/functional-acceptance.md)、[SO清单](history/native-inventory.json)。登录库静态子报告早于后续离线测试，其“尚未执行”不能覆盖后来的测试结果。

## 3. 范围、优先级与页面布局

### 3.1 已确认的范围边界

| 优先级 | 功能 | 交付范围 |
|---|---|---|
| P0 核心收听 | 搜索、专辑、节目列表、在线播放 | 免费内容真实闭环；无账号也可使用 |
| P0 核心收听 | 播放控制、队列、后台、系统媒体控制 | 暂停、进度、倍速、前后集、快进/回退、定时停止；锁屏与耳机操作 |
| P0 核心收听 | 本地资料库 | 历史、断点、队列、搜索历史、本地关注专辑；杀进程可恢复 |
| P1 账号收听 | 官方登录、会话保持、订阅、云历史 | 首次只接一种验证可用的登录方式；遵循已有账号内容权益 |
| P2 最低优先级 | 直播观看/收听、必要入房能力 | 在核心版交付后独立验证与实现，不作为首页主入口 |
| P2 最低优先级 | 非广告任务 | 仅已确认的签到/收听任务及服务端核验；不干扰播放 |
| 明确排除 | 支付、充值、礼物、打赏 | 包括已有余额消费、订单、钱包、支付 SDK、付费开通和购买跳转 |
| 暂不纳入 | 离线下载 | 不建立下载器、下载列表、离线媒体解密或导出；在线缓冲不等于下载产品 |

不做支付不等于屏蔽账号已经合法获得的可播放内容：账号内容授权仍需验证。无权益时呈现“当前账号无收听权限”等状态，不提供购买按钮。直播与任务保留为后续阶段，不能在核心版里虚报为已完成。

### 3.2 Apple 播客布局与 MD3 的分工（设计建议）

仅借鉴内容层级与页面布局：大标题、专辑封面、横向内容分组、节目纵向列表、资料库、跨页迷你播放器和完整播放页。不复制 Apple 图标素材、字体、毛玻璃、iOS 导航或系统手势；操作反馈和组件使用 Android/MD3 规范。

按用户2026-11-10确认，底部改为三个入口：**首页、发现、资料库**；搜索从首页和发现页顶部进入完整页面，返回保留原页面与搜索状态；账号与设置从首页或资料库标题区进入，不单独占底栏。直播和任务仅在后续阶段通过次级入口进入。此布局是适配建议，不宣称逐像素复刻某个 iOS 版本。

| 页面 | 布局和主要操作 | MD3 实现方向 |
|---|---|---|
| 首页 | 大标题；继续收听置顶，最近播放及已支持内容横向分组 | TopAppBar、LazyColumn/LazyRow、内容卡片 |
| 发现 | 专辑/分类封面与节目分组；只映射已核实的普通内容 | 网格与分组标题；不放推广轮播/营销卡 |
| 资料库 | 关注专辑封面网格、历史和队列入口；登录后增加云订阅 | 筛选 Chip、列表/网格、明确本地/云状态 |
| 搜索（顶部入口） | 搜索输入、历史、专辑结果、分页；返回原页 | MD3 搜索组件、Tab、LazyColumn；请求取消和去重 |
| 专辑详情 | 顶部封面、标题、简介、关注/播放；下方排序和节目列表 | MD3 按钮、列表、溢出菜单；长标题可换行 |
| 迷你播放器 | 固定在底部导航上方；小封面、标题、播放/暂停、快进 | Surface、自定义内容排列；点击进入完整播放器 |
| 完整播放器 | 大封面→标题/专辑→进度→回退/播放/快进→倍速/定时/队列 | Slider、IconButton、ModalBottomSheet；竖屏全页，返回关闭 |
| 设置/账号 | 账号状态、播放偏好、缓存清理和诊断入口 | MD3 设置列表；无钱包、充值或会员购买入口 |

发现页按主题缓存公开专辑元数据，已有缓存进入即显示；首次无缓存加载、用户下拉/主动刷新和按需分页才请求。刷新失败保留内容；各主题记住滚动，进程重开恢复最多前10页缓存，不含身份或播放地址。

迷你播放器属于应用外壳，不随页面重新创建播放实例；完整播放器打开和关闭不重启播放。无当前节目时隐藏迷你播放器。发现接口若没有可验证的数据源，展示明确空态，不以随机推荐或内置假内容充数。

### 3.3 配色、适配与交互验收

- 使用喜马拉雅橙红方向作为主色参考，建立 `primary/onPrimary/surface/onSurface/error` 等 MD3 语义色；具体色值从现有资源核对后确定，不将猜测 HEX 当作官方色值。
- 提供浅色/深色两套主题。默认品牌色；不让壁纸动态色替换品牌主色。正文和封面之外的大面积背景保持易读。
- 用系统字体、MD3 字阶和组件触摸范围；普通文字对比度至少 4.5:1，大字至少 3:1；检查 TalkBack 标签、焦点顺序和大字体。
- Edge-to-edge 布局正确处理状态栏、导航栏、键盘和安全区；底部列表不被迷你播放器遮挡；支持 Android 返回及预测性返回。
- 手机为首轮目标；按窗口宽度适配，宽屏可使用 NavigationRail 和列表/详情布局，不复制手机固定宽度。旋转、分屏和字体放大不得遮挡主播放按钮。
- 每个数据页具有加载、空、错误、正常状态；切换底栏保留滚动与查询状态；网络错误就地重试，避免连续弹窗。

Apple 的公开使用指南可作为 MiniPlayer、完整播放器和资料库等布局参考：[Apple Podcasts 使用指南](https://support.apple.com/guide/iphone/play-podcasts-on-iphone-iph3a22707a5/ios)。本文页面安排和品牌色应用属于本项目设计建议，并非 Apple 官方设计规范。

### 3.4 广告和弹窗

不集成广告或激励 SDK，不建立营销弹窗调度器。服务端未知组件不自动执行；普通内容与广告任务按业务类型区分，不整域封禁共享服务。保留用户主动登录、验证码/风控、操作错误和系统媒体通知。媒体本身的口播广告没有已验证分段信息时，不承诺自动剪除。

## 4. Android 技术架构（2026-11-06 核对）

### 4.1 推荐技术与收益

“最新推荐”按官方推荐路线与稳定发布版本执行，不机械选择版本号最高的预览版；工程建立时记录版本目录与兼容性检查结果。历史协议兼容被隔离，不要求新 UI、播放器和控制逻辑沿用原实现。

| 层 | 设计建议 | 收益与边界 |
|---|---|---|
| 语言/界面 | Kotlin、Single Activity、Jetpack Compose、Material 3 | 原生声明式 UI；替换原 View/XML + ViewBinding 优先建议；Java 仅用于确需准确签名的 JNI 桥接 |
| 导航 | Navigation 3 | 使用 Compose 导航和可保存返回栈；覆盖底栏独立栈、播放页、账号页和返回行为 |
| 状态 | ViewModel、Coroutines、StateFlow、单向数据流 | UI 发送事件，状态统一输出；使用生命周期感知收集，不在 Composable 中直接发业务请求 |
| 数据层 | Repository + 本地/远端数据源 | 统一错误、缓存和账号边界；仅复用复杂业务规则时增加 use case，不预设厚 domain 层 |
| HTTP/JSON | OkHttp + kotlinx.serialization | 集中身份范围、签名、超时与解析；原始序列化必须兼容上游签名，不能默认重排 JSON 字段 |
| 播放 | AndroidX Media3 ExoPlayer、MediaSessionService、MediaController | 播放服务独立于页面；系统通知/锁屏/蓝牙控制共用单一状态源；按实际媒体格式增加模块 |
| 本地数据 | Room；设置用 DataStore；凭据用 Keystore 加密 | 历史与队列事务持久化；DataStore/Room 不自动提供凭据加密 |
| 图片 | Coil 的 Compose 集成 | 单一图片管线，有界缓存；不继承账号请求头 |
| 依赖注入 | 小型应用先构造器注入与单一应用容器 | 避免逐页创建 Session/Player/Repository；复杂度增长后再评估 Hilt，不并用多套容器 |
| 持久后台工作 | 需要云同步补报后再引入 WorkManager | 支持网络条件与退避；不承担持续播放、精确计时或实时心跳 |
| 构建 | Gradle Kotlin DSL、版本目录、Compose BOM、稳定工具链、R8 | 管理兼容版本；Room 等代码生成优先 KSP；release 产物测体积和性能 |
| 服务端 | 首期设备直连，不新建业务后端 | 避免增加无证据的服务器和账号中转需求 |

官方架构文档推荐 Compose、分层、单向数据流与 ViewModel，并推荐 Navigation 3；这是路线依据，表内具体网络库、图片库和模块划分为本项目选择：[架构建议](https://developer.android.com/topic/architecture/recommendations)。

Compose Material 3 提供 MD3 主题与组件；新组件及 Material 3 Expressive 按稳定性和布局收益选择，不为追新改动 Apple 播客布局目标：[Material 3](https://developer.android.com/develop/ui/compose/designsystems/material3)。Navigation 3 已有稳定发布，选版应查看 stable 栏而非直接复制可能指向 alpha 的依赖示例：[Navigation 3 发布记录](https://developer.android.com/jetpack/androidx/releases/navigation3)。

### 4.2 模块与单一状态源

先保持两个必需 Gradle 模块与一个条件模块：

```text
app/
  ui/               Compose、MD3主题、导航、页面、ViewModel
  playback/         MediaSessionService、队列、音频焦点、恢复
  data/             Repository、Room、DataStore、会话与同步
protocol/
  content/          搜索、专辑、声音
  playback/         BaseInfo、授权、媒体地址解析
  account/          Passport、会话材料与业务ticket
  transport/        HTTP、错误、身份范围、签名调度
  live/             P2阶段才增加：房间和流信息
  task/             P2阶段才增加：非广告类型、进度和领取
native-compat/      必要时建立：准确JNI桥接、已验证函数
```

UI → ViewModel → Repository → 本地/协议适配；UI 通过 MediaController 连接播放服务，不能由页面持有第二个 ExoPlayer。SessionManager 集中管理账号 generation；PlaybackService 持有唯一播放器和实时队列；Room 保存可恢复快照，进度落库节流。默认单进程，不先引入 IPC、动态插件、RN 或原多进程框架。

[Media3 后台播放文档](https://developer.android.com/media/media3/session/background-playback)规定的服务、会话和控制器职责用作播放实现依据；后台服务声明及限制按最终 targetSdk 校验。

### 4.3 SDK、设备和旧 native 的边界

compileSdk/targetSdk 在开工时选择当时最新稳定 Android SDK，结合官方行为变更及库要求验证；不继续以“本机只有 SDK 36”为长期技术约束，也不在未检查前虚报精确最新版。升级目标 SDK 与提高最低版本是两回事。

minSdk 暂保留 26 为待确认建议，首轮 ARM64；阶段 0 根据用户设备确认最低支持版本。如果不满足最新稳定依赖最低要求，应明确取舍，不能悄悄退回旧技术。x86/32 位及其他设备不作未经测试的承诺。native 兼容与 16KB 页大小见第 6 节。

## 5. 接口适配与请求控制

### 5.1 最小接口集合

以下是样本代码已定位的路径，不是本轮重新验证过的在线接口清单。精确构参和源文件行号见原静态报告第二、三章。

| 业务 | 已定位路径 | 新实现关注点 |
|---|---|---|
| 搜索 | `search.ximalaya.com/[hub/]front/v1`，POST JSON | kw、core、page/rows、筛选与searchMeta等上下文；不可只传一个keyword就假定等价 |
| 专辑 | `mobile.ximalaya.com/mobile-album/album/page/ts-{ts}` | albumId、分页、排序、设备和权限字段 |
| 声音列表 | `mobile/v1/album/track/ts-{ts}`及样本中的v2变体 | 保留实际路由，不能凭名字自行修正URL拼接 |
| 播放 | `mobile-playpage/track/v3/baseInfo/{ts}`、`v4/baseInfo/{ts}` | sign、x-tk、音质/能力、授权与加密URL版本 |
| 内容授权/防盗链 | `mpay.ximalaya.com/mobile/track/pay/v2/{id}/ts-{ts}` | 仅在已有内容授权解析确实需要时验证；路径含pay不等于下单支付，不实现购买或扣款 |
| 订阅 | `subscribe/album/subscribe/create`、`delete`、订阅列表 | 需要会话；写入失败可恢复状态 |
| 云历史 | `nyx/v1/history/query/android`与merge等写路径 | 查询与写入主机不同；账号隔离与离线补报 |
| 登录 | Passport nonce、sms、quick、pwd、check、refresh、logout | 详情见第7节；不得将所有身份材料合并成一个token |
| 直播入房事件 | `live.ximalaya.com/lamia/v5/live/user_entry` | 业务事件，不是流地址，不作为拉流成功判断 |
| 直播房间/任务 | 已定位调用类和部分路由工厂 | 各自阶段补齐每种保留业务的请求/解析/结果链；本文不编造尚未完整核实的URL和参数 |

接口契约直接忠实适配上游，不要求上游改成新JSON包装。客户端内部统一返回成功数据、业务失败、网络失败、需要登录、需要验证、权限不足等类型，保留可诊断的上游错误码。

### 5.2 身份、设备材料和媒体请求分开

- **业务HTTP客户端**：只向相应业务主机发送所需Cookie/签名/ticket。
- **Passport客户端**：执行登录挑战与会话协议；不让通用重试重复发送短信。
- **媒体HTTP客户端**：使用响应规定的媒体地址与必要媒体头，不把账号Cookie、x-tk自动附到任意CDN或重定向主机。
- **图片请求**：不默认继承账号身份。

会话在内存集中管理，签名在最终业务参数确定后生成。不同接口的排序、空值、编码、JSON与query语义分别按证据固定，不能套一个万能签名函数。

设备ID保持稳定，隐私同意后按协议收集确有必要的材料；Xuid/x-tk归于业务认证能力评估，不因它与埋点/广告共用框架就直接删掉。缺少材料时记录明确的接口失败原因，不用每次随机新设备ID掩盖问题。

只读请求允许有限重试和退避；失效媒体URL先刷新解析，避免无限重播同一个403。短信发送、领奖不能以通用网络重试自动重发。服务端未确认支持幂等参数时，不向请求中自行添加字段并宣称幂等已实现。

## 6. SO与加密兼容层：先验证，再决定保留方式

### 6.1 每个核心库的处置

| 库 | 原始未压缩大小 | 方案 |
|---|---:|---|
| `libencrypt.so` | 584,160字节 | 先列出播放解析、通用签名等实际用到的函数和依赖。优先复原必要业务算法并做对照；若仍需包装原库，先验证独立应用身份、资源、初始化和稳定性，不能把隐藏PNG更新直接当成独立移植已完成 |
| `liblogin_encrypt.so` | 133,576字节 | 优先把字段转换、完整signature和产品分支分别验证。可保留准确JNI桥接进行对照，但只有RSA成功不足以进入登录功能验收 |
| `liblive_encrypt.so` | 14,088字节 | 验证入房签名及真实流地址解密所需分支。原Java会把实际Context包名交给getCourseKeyNative；合成字符串测试不证明新包实际链能用 |

四个小型业务相关SO总共约0.71MiB未压缩，其自身不是原包体积的主要来源。这不包含它们在Java层、资源、初始化和业务认证上的依赖。旧JSC约8.52MiB、Hermes约3.21MiB、IJK FFmpeg约6.67MiB未压缩，可说明避免全量引擎的方向；不能把这些未压缩数字直接相加，当作最终APK节省量。

### 6.2 兼容实验的验收方法

1. 从样本确认每个实际使用JNI的类名、方法签名、返回、异常和资源依赖。JNI声明的Java包路径可以与新App的applicationId不同，二者不可混为一谈。
2. 在新applicationId、自己的签名和真实Context下验证，不能只把一个字符串参数换成原包名就宣称身份兼容。
3. 用合成输入做原行为与新实现对照：摘要逐字一致；随机RSA验证可解码长度/格式和调用稳定性，不要求随机密文相同；媒体转换使用已知输入的回环与边界样本。
4. 加入缺资源、空输入、非法Base64、错误地址版本、并发调用、进程重建等路径，检查是否崩溃或错误退出。
5. 对真实公开播放响应做地址解析和实际媒体读取，才算播放兼容；仅能加载SO、返回非空不能通过。
6. release构建启用R8后再次运行；保留确需静态JNI查找的类/方法，检查FindClass依赖，不能仅保留Java native声明就假定充分。

不把Frida、Hook或修改系统API作为用户安装包的运行依赖。兼容层无法脱离整套原Application时，暂停扩展页面，报告具体缺口和依赖增量，再决定继续复原还是采用正式SDK能力。

### 6.3 Android与ABI兼容

首轮 ARM64；最低版本与最新稳定 compileSdk/targetSdk 的选定方法以第 4.3 节为准。不能因现有探针只运行于 Android 14 就将新客户端限制在旧 SDK。

已有运行结果主要来自Android14/ARM64/4KB页设备，**不证明16KB兼容**。新工程同时检查ELF LOAD/RELRO布局和APK打包对齐，并在16KB设备实际加载和执行业务函数；单独zipalign通过不能替代ELF及运行检查。预编译SO没有源码时，无法假定升级本工程NDK就会重建它，必要时需要兼容版本或重新实现该最小功能。[Android页大小文档](https://developer.android.com/guide/practices/page-sizes)

## 7. 官方登录与会话保持

### 7.1 接入路线与优先级

**推荐先验证原App Passport协议能否在新客户端身份下正确使用。** 它与现有逆向目标和原App账号能力更接近，但兼容性尚未证明。

开放平台授权作为条件备选：必须先取得可读、适用的官方文档、自己的应用配置及实际权限范围，再判断能否覆盖原App的收听、订阅、云历史和后续直播/任务。不能把开放平台accessToken直接塞入原Cookie。当前公开页面不足以证明全部所需权限可取得；本轮核验的[开放平台页面](https://open.ximalaya.com/doc/detailApi?articleId=60&categoryId=9)没有可读正文，不据此补造接入参数。

首次建议只完成一种明确的官方账号登录方式，优先研究短信链路；密码、微信/QQ、运营商一键登录属于独立能力。尤其第三方登录SDK是否允许当前包名、签名和应用配置，需要单独确认，不能复制原AppId就视为能用。

### 7.2 Passport流程

以样本短信链为设计依据：

```text
用户主动登录
  → 获取 mobile/nonce/{ts}
  → 按协议转换字段、生成signature
  → mobile/sms/v3/send
  → 用户输入短信码
  → mobile/sms/v2/verify，取得bizKey
  → mobile/login/quick/v2，使用smsKey完成登录
  → 校验响应、原子保存会话
  → 重新请求账号业务与内容授权
```

每步使用正确的挑战材料和业务参数；若返回官方验证码/风控验证，呈现所需主动流程并等待用户完成。不能用自动重试反复发验证码，也不能将风控失败呈现为“已登录”。

已定位的凭据分层：

| 材料 | 客户端处理 |
|---|---|
| uid/token | 账号会话，样本自定义Cookie结构为 `1&_token=<uid>&<token>;` |
| nonce/bizKey等 | 短期流程状态，按真实响应生命周期处理，不做永久配置 |
| signature | 依据当前请求生成，不缓存成所有请求共用的凭据 |
| Xuid/设备头 | 按必要业务认证协议生成并作用于正确请求 |
| x-tk | 业务相关ticket，与账号token分开管理 |
| 媒体URL参数 | 按声音、音质、授权和有效期使用，不作为账号登录态 |

### 7.3 登录保持与并发处理

建议账号状态为：`Guest → Authenticating → SignedIn`，恢复后可处于 `Restoring/Checking`；另有 `NeedsVerification/Expired/LoggingOut`。网络不可用只标记暂时无法校验，不将其自动等同于凭据被撤销。

- Keystore保存加密密钥，凭据密文保存在App私有存储；DataStore或Room本身不是凭据加密措施。[Android Keystore文档](https://developer.android.com/privacy-and-security/keystore)
- 不保存密码或短信码，不把账号token、完整Cookie、ticket、含签名媒体URL写入日志或导出诊断。
- 重启恢复只表示读到本地凭据，随后按业务需要做check；不因token非空就标为服务端确认有效。
- 刷新由一个SessionManager集中调度，合并并发请求。提交响应前比对uid、请求token与当前会话generation，避免退出或换号后的旧响应覆盖新状态。
- `user-http-app/v1/token/refresh`响应须按协议处理refreshable、oldToken/newToken；内存与持久化更新保持一致。
- 样本前台检查有24小时门控，但每次检查都更新时间。这是样本行为，不能据此承诺永久登录，也不建议原样复制其失败/频繁前台时的时间戳问题。新实现分别记录检查尝试与成功，具体刷新策略以验证结果决定。
- 遇到样本业务ret=50等失效信号，先走指定login/check语义，避免将所有HTTP401都视为同一种可刷新错误。
- 退出立即递增generation、阻止旧回调提交、清除本地会话与有关WebView会话、取消账号工作；服务端logout失败应有明确结果，不无限阻塞本地退出。
- 账号切换后，云历史、订阅和任务全部按owner_uid隔离。允许匿名继续收听的行为不需要等待账号任务。

此节是设计。当前范围不执行验证码、真实登录或会话刷新；后续只有真实账号重启/失效/刷新/退出验证通过，才能接受“官方登录及保持已实现”。

## 8. 音频播放与本地状态

### 8.1 完整播放链

1. 用户选择trackId，取得基本信息及需要的授权状态。
2. 选择已验证的BaseInfo版本，组装签名、业务ticket、音质能力参数。v3/v4分别有证据才启用，不能把任意失败都自动切旧接口。
3. 解析isAuthorized、试听边界、授权到期和多音质候选；权限不足作为明确状态。
4. 按响应url版本完成地址解密和必要防盗链构造，得到本次可用媒体地址。
5. Media3通过独立媒体请求层播放；解密、请求、播放器错误可分别诊断。
6. URL过期时有限次数重新解析，保留播放位置；当前账号已无权限时停止并说明。
7. track结束后按队列解析下一条；下一条的广告/任务状态不成为播放前置条件。

服务端返回的授权和试听长度必须进入模型；下载字段不开放下载入口。当前定位的主要播放接口来自样本，独立包真实响应与时效仍需实测。

### 8.2 服务与恢复

PlaybackService持有唯一播放实例；页面、迷你播放器、通知和蓝牙控制共同观察它的状态。处理音频焦点丢失、耳机拔出、来电、暂停、网络切换、重复点击、服务销毁和设备锁屏。首次点播放后应立即显示解析/缓冲反馈，不能等网络返回才响应。

保存trackId、队列索引、播放位置、倍速、更新时间；不把短期媒体URL当成长期恢复依据。进程重建先恢复界面与队列，再取得可用地址；不因打开App就擅自自动播放。暂停及切换时及时保存，播放过程中按节流间隔落库，避免每个进度回调写数据库。

### 8.3 数据设计范围

| 数据 | 建议关键字段/规则 |
|---|---|
| play_history | owner_uid或明确guest、track_id、album_id、position_ms、duration_ms、played_at、created_at、updated_at；owner与track唯一 |
| queue_item | queue_id、ordinal、track_id、owner_uid、created_at、updated_at；队列重排事务提交 |
| content_cache | 业务ID、解析后的必要元数据、获取时间、失效条件；不含长期有效媒体地址假设 |
| sync_outbox | owner_uid、操作类型、本地operation_id、状态、重试时间、created_at、updated_at；本地ID不冒充服务器幂等支持 |
| local_follow | owner_uid或guest、album_id、关注时间；本地关注与云订阅分开，不默认批量写入账号 |

任务进度以服务端响应为准；本地计时只提供交互反馈或待提交行为，不能冒充已获奖励。本文不生成DDL或初始化数据库，待协议样本和实际存储需求明确后随实现提交迁移。

## 9. 最低优先级：直播与必要入房能力

仅在第 6 阶段核心版交付后进入；不提前引入直播 SDK、IM 常驻连接或房间入口。房间详情、流地址、解密、实际播放、状态更新分别验证。现有离线签名和 key 分支测试不代表真实房间可播。

| 子链 | 最小范围 | 验收 |
|---|---|---|
| 房间详情 | roomId、主播、开播/结束/无权限、媒体候选 | 真实开播房间返回有效数据，结束状态明确 |
| 拉流 | 优先复用 Media3 可处理的实际 HTTP-FLV/HLS | 实际出声/出画、切房、断网重连和退房 |
| 必要入房协议 | 仅观看所必需的签名、事件、心跳；必要时最小 IM | 服务端确认、断线恢复、退出清理；不能用发送成功冒充确认 |
| 与节目切换 | 直播/点播互斥使用同一播放协调入口 | 不双重出声，切回节目恢复正确队列/位置 |

Media3 容器支持不代表支持所有传输协议、编码或 RTC 房型：[格式文档](https://developer.android.com/media/media3/exoplayer/supported-formats)。先验证真实媒体，再评估额外引擎收益、体积与兼容成本。不能播放的房型列明缺口；不以首页封面充当完成证据。

开播、连麦、录音、相机、社交聊天和公屏特效不因观看需求自动纳入。是否必须支持 RTC 房型在该阶段开始前确认，不申请无对应功能的麦克风/相机权限。换房及换号递增连接 generation，丢弃旧消息；离开房间关闭连接。

**支付、充值、余额消费、礼物目录与发送、打赏、钱包、订单及礼物动画全部不实现。** 不保留灰色入口、占位按钮、外部购买跳转或交易数据表。

## 10. 非广告任务和推广过滤

任务仅在最低优先级阶段按**业务类型白名单**实现：已经确认的签到、收听等非广告任务才出现；广告观看、充值/消费/送礼、推广跳转以及未知类型不作为普通任务展示。不能靠文案含不含“视频”判断，不能只按adse等主机名整域封禁，因为同一业务系统可能同时承载保留任务与广告任务。

每类任务必须补齐：列表/资格、服务端任务ID、条件、触发动作、进度上报、领取、结果校验和错误处理。当前SevenVideoTaskView及FreeListenSevenVideoTaskInfo证明同组件混合广告与收听任务，不能把原整组件复制进来再隐藏一个按钮。

建议任务状态：不可参与、可参与、进行中、可领取、领取中、已领取、待确认、失败。收听计时来自真实播放状态，暂停/缓冲/拖动不直接计为有效收听；服务端具体计时协议、最低上报频率和认定条件必须进一步取证，不在方案中编造。

领奖提交后遇到超时，先核对服务端任务状态再决定是否允许重试；不能本地直接加余额、时长或权益。界面只在用户进入任务页或主动领取时操作，不在播放页弹自动领奖推广窗。

推荐流采用显式映射：声音/专辑/主播等已支持内容进入展示模型；广告、付费促销、远程弹窗、陌生schema和未支持组件不自动执行。H5仅用于确有必要且用户主动发起的官方流程，限定跳转和桥接能力，避免把整个营销容器重新带回来。

**客户端可保证不实现广告SDK和已识别推广组件；不能保证服务端音频或主播直播内容里没有口播广告。** 如果媒体本身含广告，没有已验证分段标记时不承诺自动剪除。

## 11. 体积、启动和权限控制

### 11.1 体积预算建议

以下沿用原方案的设计评审预算，不是实测值或最终承诺，单位MiB。以签名后的ARM64 release APK衡量；同时记录实际安装空间和首次运行缓存。

| 里程碑 | 建议预算 | 超出时的处理 |
|---|---:|---|
| 独立匿名搜索/专辑/播放 | ≤20 | 输出依赖、DEX、资源、SO分类体积，逐项确认必要性 |
| 核心账号版及后续扩展 | ≤35 | 分别测量核心版与P2增量；Compose、认证或必要直播依赖超预算时列明增量，不通过回退旧UI方案来隐性达标 |

不承诺固定5MiB或10MiB。现有证据支持减少全量框架依赖的方向，没有新工程产物可证明最终数值。

措施：只打包需要的ABI；按需引入Media3协议模块；不集成IMA等广告模块；不带原RN bundle、通用插件和礼物特效素材；R8/资源裁剪；对JNI保留规则做准确约束；不同时引入多套JSON、图片或播放引擎。所有remote图片/媒体设有界缓存和清理入口。

### 11.2 启动与权限

Application只做本地轻量初始化。首页不等待登录刷新、任务、IM或远程营销配置；播放器按首次需要准备；直播连接随房间生命周期启动和关闭。设置页可以显示诊断信息，普通用户流程不暴露加密实现细节。

权限按实现和Android版本确定：基础联网、当前媒体播放所需前台服务/通知能力；不为播放强制申请悬浮窗、定位、通讯录、短信读取、全盘文件或安装权限。媒体通知与服务声明按平台文档处理，不能通过静默删除通知来“精简”。

性能先建立新包与精简候选在同一设备的冷启动、首屏、首次出声、峰值内存和后台耗电基线；暂不编造启动耗时承诺。依赖优化必须同时确认真实功能与错误恢复没有回退。

**任务与交付：** 重跑受影响核心流程、release/16KB/依赖/权限/体积检查；核对直播/任务没有常驻耗电、双重播放或广告回流；交付带明确扩展范围和哈希的 release。

**验收：** 核心收听无回退；扩展能力逐项有真实证据；明确排除项仍无入口和依赖。

### 停止扩展条件

独立播放必须依赖大规模原框架、必要 native 在目标设备不可运行、账号身份无法通过、未知风控或协议变化时，定位证据与新增成本，再评审对应关卡。直播失败不回头阻断核心版；支付、充值、礼物打赏和离线下载不得作为“解决依赖”被重新纳入。

## 14. 验收矩阵与复现方法

### 14.1 核心版

| 范围 | 检查 | 通过依据 |
|---|---|---|
| 内容 | 中文/空格/无结果、分页、请求取消；真实专辑和节目 | 真实接口结果及页面状态匹配 |
| 播放 | 拖动、倍速、队列重排、连播、快进回退、定时 | UI、服务、系统控制一致；至少连续30分钟观察 |
| 系统 | 后台/锁屏/蓝牙、焦点、拔耳机、来电、网络切换 | 真实设备行为及错误恢复，无双重音频 |
| 恢复 | 系统回收进程、重启、短期URL过期 | 历史/队列/断点正确，主动播放再解析，无擅自开播 |
| UI | 第3节布局、浅深色、大字体、TalkBack、窄/宽窗、键盘 | 页面截图及实际交互；对比度、触摸和遮挡检查 |
| 账号 | 成败/取消/风控、重启/check/refresh/退出/换号 | 真实账号及服务端最终状态；未实测明确未验收 |
| 同步 | 订阅、取消、云历史、离线补报、旧回调 | 不串号、不重复错误提交，端云结果可核对 |
| 权益 | 已有权益与无权限节目 | 遵守授权/试听，无付费入口，不绕过权限 |
| 范围 | 广告/营销/购买/充值/礼物/打赏/下载 | UI、依赖、Manifest及实际请求检查；不仅搜索类名 |
| 兼容 | 最低/中间/最新稳定系统、ARM64、4KB/16KB | release安装及必要JNI/播放真实运行 |

账号操作仍需要后续明确的实测安排；本轮方案更新不发送验证码、不登录、不执行云写入。

### 14.2 P2 扩展版

直播按房型逐一验证实际媒体、入房、结束、重连、换房和与节目切换；非广告任务核对资格、真实进度、领取失败/超时和服务端最终结果。必要错误路径可注入故障，正常能力不得用 Mock 通过。另检查消费型任务不可见、无礼物/支付入口、连接释放与核心播放回归。

## 15. 风险与维护

| 风险 | 处理与影响边界 |
|---|---|
| 新包身份/签名无法通过协议 | 阶段1和5A先验证；播放阻塞时暂停完整UI，账号阻塞不虚报兼容 |
| 旧SO初始化/16KB问题 | 最小算法优先，原SO必要性有证据；不假定升级NDK会重建无源码预编译库 |
| 新版SDK和库的行为变化 | 开工选稳定组合，记录系统变更；发布前真实回归，不套用本机旧SDK限制 |
| Compose或认证依赖增大体积 | 以release实测拆分依赖，保留现代UI路线；预算为评审目标 |
| 服务端字段/授权变化 | 协议集中适配，未知类型有明确状态，不在页面散布URL |
| 云同步冲突或跨账号回调 | owner隔离、generation和outbox；按真实服务端语义确认，不编造幂等支持 |
| 直播额外引擎/IM耗电 | P2阶段单独评估，不常驻、不阻塞核心发布 |
| 任务/推荐混入广告或消费 | 类型白名单、未知不执行；消费/充值/礼物任务排除 |

新应用独立包名与签名，可与官方/精简候选共存；测试签名与长期发布签名分开，长期签名保持稳定。卸载独立包可退回原应用，但会清除独立包本地数据，不能作为无损数据库回滚手段。后续数据库升级带迁移及验证；不将删除数据库当作常规升级修复。

诊断只记录路径模板、阶段、错误码、耗时等脱敏信息，不导出 Cookie、ticket、短信、账号token或带签名媒体URL。协议维护保留样本版本及既有证据，不增加服务端远程代码或任意schema执行能力。

**应用原则：** 收益优先、遵循标准、成熟稳定组件、集中播放/会话控制、实证优先；使用成熟AndroidX组件，业务协议边界自行适配，不自研播放器框架。

**代价：** 新客户端仍承担协议/native维护；Compose体积、服务端身份接受、账号风控和各直播房型兼容必须实测，不用旧框架绕开验证。

**未决事项：** 阶段0确认最低设备版本及具体稳定版本组合；阶段5确认首次登录方式和账号实测安排；阶段7确认房型覆盖。它们是未来阶段的输入，不代表本轮详细计划留有占位，也不授权提前实施。
