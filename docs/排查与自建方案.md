# 重签退出排查与自建 App 方案

日期：2026-11-04。范围：用户提供的 APK；隔离模拟器诊断；评估自行实现。没有测试真实登录、支付、打赏或领奖。

## 结论与决策依据

**SO 逆向已打通重签名基线：仅修改隐藏配置的测试签名包可进入首页并播放公开声音。当前继续原 APK 的功能裁剪，没有必要因先前的启动问题直接转向重写。** 自建方案作为备选保留，其完整替代能力尚未证实。

原始 APK 未修改。此前的原版未登录搜索和播放仍单独作为原版基线；本轮新增了重签修正包的独立播放证据。功能裁剪修订6已完成构建及下述匿名功能复验，当前作为测试签名候选提供；没有把未测的登录、直播、打赏与领奖算作通过。

## 功能精简候选与实际验证

候选 APK：[ximalaya_slim_test.apk](artifacts/ximalaya_slim_test.apk)。SHA-256：`63d568e2eecb4ef3a5af7bb15d8af89b05c8694654099fead566ed94a6b6c260`。体积 122,712,636 字节（117.03 MiB），原包 124,973,695 字节（119.18 MiB），减少 1.81%。这是功能精简候选，不能称为已经大幅压缩。

已修改的行为与原因：

- 开屏走原有跳过分支；播放贴片返回原有空广告结果；聚合请求走原有拦截错误回调，避免播放等待广告完成。
- 禁用 GDT 初始化走原有失败通知路径，删除其插件 JAR。没有直接删除仍可能被调用的 native 库。
- 已识别的广告推广、召回、订阅引导、会员页签和月卡预售 Bar 不展示；普通首页内容、快听、我的保留。
- 广告奖励任务和视频领时长入口隐藏；收听等非广告任务代码保留。混合时长弹窗仅过滤自动场景与广告状态，保留主动操作和非广告领取/错误分支。
- 登录、礼物选择和支付确认没有全局屏蔽。没有修改账号或内容权益，没有伪造奖励完成。

隔离 Android 14 ARM64 模拟器中，修订6已实测：清空数据进入首页、匿名搜索“大明演义”、完整播放页播放/暂停/恢复、切后台继续播放、返回前台、断网错误提示与恢复网络搜索。首次返回的悬浮锁屏权限说明保留；关闭后再次返回没有上一修订的“看视频领时长”窗口。媒体会话从 PLAYING 45,030ms，经 PAUSED 82,206ms，恢复后后台 PLAYING 244,229ms；整个流程主进程PID10406保持不变，没有注入原App。截图、XML、会话原文见[修订6验收记录](evidence/functional-acceptance.md)。

最终载荷只改变六个 DEX 和隐藏校验 PNG，删除 GDT 插件 JAR；Manifest、其余九个 DEX、全部87个SO后缀成员字节不变。14个smali文件有原始副本和逐方法差异，见[载荷比较](evidence/slim-payload-comparison-r6.json)、[方法保留核对](evidence/source-diff-check-r6.json)、[补丁差异](evidence/promotions-functional.diff)。签名与ZIP对齐检查通过。

**尚未验证：** 实际直播拉流、真实登录及会话恢复、支付/打赏、服务端任务领奖；这些功能的代码保留不能作为运行通过。未覆盖全部远程AB、H5/RN推广，也未证明所有广告SDK完全停止网络初始化。当前包使用测试签名，不能覆盖原官方签名安装；请在隔离模拟器使用，不要为测试删除已有账号数据。

复验与回滚：在隔离 Android14 ARM64 设备安装同哈希候选，按验收记录顺序操作；不涉及登录。回滚只需卸载隔离设备中的候选并装回原包，原始 `ximalaya_app.apk` 保持不变。工作目录的探针APK仅用于诊断，不能作为交付包。

## 这轮实际排查

### 1. 将包内容问题与签名变化分开

此前仅重签对照有 23,192 个非签名 ZIP 成员内容与原包一致，仍不能稳定启动；完整反编译重建也失败。它排除了“必须先裁剪才会坏”的解释，但没有排除 ZIP 布局、证书、初始化状态及 native 逻辑的影响。不能直接写成“已经证实反篡改”。

证据：[成员比较](evidence/resigned-comparison.json)、[原基线记录](evidence/基线验证.md)。

### 2. 新捕获到 OAID 库初始化崩溃

仅重签包在 Android 14/ARM64/4 KB 页模拟器中运行只读 native 探针时，发生 SIGSEGV，故障地址为 `0x000b0002000095ca`。栈顶是 `libmsaoaidsec.so+0x20d10`，其后是该库的构造函数与动态链接器加载流程。

Java 调用链可定位为：

`PrivacyPolicyDialogFragment.i → host.util.ce.a → ce.b → com.ximalaya.ting.a.b.a → System.loadLibrary("msaoaidsec")`

其中 `analysis/jadx/sources/com/ximalaya/ting/a/b.java:52` 明确加载此库，`:66` 随后初始化 `MdidSdkHelper`。`host/util/ce.java:130` 起接入 OAID 回调和广告标识缓存。

**证据边界：这是探针环境下的崩溃，不足以判定 OAID 是所有退出的根因。** 此次未进入预期的 `libencrypt.so` 目标函数，因此不能拿这一轮的 SIGSEGV 解释此前该库的非法释放。探针可能改变 native 环境或时序。

证据：[崩溃头与调用栈](evidence/oaid-probe-crash.txt)、[只读探针](work/inspect_native.py)、[原包探针记录](evidence/original-native-inspection.txt)、[重签包探针记录](evidence/resigned-native-inspection.txt)。

### 3. 去掉运行时探针后仍然退出

停止 Frida 服务、重新启动仅重签包后，系统记录仍出现 `EXIT_SELF`，状态分别为 1、0，也存在 SIGSEGV。说明不能只把问题归因于这次诊断工具。

证据：[无探针的系统退出记录](evidence/resigned-without-probe-exit-info.txt)。记录包含启动后的多次重启，不能把所有 PID 都当作同一次前台启动。

### 4. Java 退出入口日志实验

构建了独立诊断包，在主 DEX 和 classes12 中的 5 个文件增加退出前 `Thread.dumpStack()`，并在两个全局异常处理器入口增加异常堆栈输出；不删除原有退出行为。修改及源文件恢复由脚本记录。

包安装并启动后主进程仍退出，本次过滤日志未捕获到新增退出堆栈。因此**未定位到被记录 Java 入口**，不能进一步断言所有退出都来自 native：还有其他 DEX、JNI 和反射等未覆盖入口。

最初跨全部 DEX 插入日志时遇到 `Unsigned short value out of range: 65536`；缩小到相关 DEX 后成功构建。它是新增诊断代码引起的构建限制，不是原 App 运行失败的原因。

证据：[诊断差异](evidence/exit-probe.diff)、[构建记录](evidence/exit-probe-build.log)、[过滤日志](evidence/exit-probe-filtered.txt)。空过滤结果只表示本次没有捕获到相应记录。

### 5. OAID 单点对照

另建诊断副本，只将 `com.ximalaya.ting.a.b.a(Context,boolean,callback)` 改为调用既有失败回调后返回，从而跳过 OAID 库初始化。副本以原 APK 为容器来源，只有 `classes11.dex` 的非签名成员内容发生变化；所有其他 DEX 和原生库沿用原包。

差异：[单点补丁](evidence/oaid-probe.diff)、[成员比较](evidence/oaid-probe-comparison.json)。这个副本用于排除故障，不是最终广告补丁，也不证明其他功能正常。

**运行结果：未稳定启动。** 在不加载 Frida 的条件下，系统记录主进程多次被信号 9 结束；记录本身不标明信号发送者。因此，单独跳过 OAID 没有解决启动，不能把 OAID 问题当作唯一根因。证据：[单点对照退出记录](evidence/oaid-only-exit-info.txt)。

这轮结束时已关闭隔离模拟器并移除诊断端口。所有临时 smali 修改均恢复，补丁差异与诊断 APK 单独留在 `implementation/`，原始 APK 保持不动。

## 优先 SO 逆向后的新增验证

### 文件清单与范围

原 ZIP 有 87 个 `.so` 后缀成员：`lib/arm64-v8a/` 中 85 个为 little-endian ELF64，合计连同另外两个 `assets/fix/` 同后缀成员为 57,007,950 字节。不能把另外两个后缀成员当作已识别的 ARM64 库。当前深入分析的是认证、请求签名、直播和媒体解密相关库，未声称已完整逆向全部 85 个库。

可复查：[ELF 清单、哈希、依赖与 JNI 导出](evidence/native-inventory.json)、[Java 加载位置](evidence/native-java-load-sites.txt)。清单来自 ELF section、DT_NEEDED 和 dynsym，不依赖文件名猜测。

### libencrypt.so：业务密码能力与完整性检查同时存在

此库不是可以随广告 SDK 一起删除的纯广告库。Java 中通用请求签名、部分播放地址解密、直播打赏等都会调用它。独立静态追踪与 native helper 运行，已确认以下结构：

1. `0xaac0` 是校验工作线程；`0xbe38` 调 `0xd5c0` 解析配置。
2. 配置藏于 `assets/drawable/x_l.png` 的 `tEXt` chunk。`0x751f0` 初始化状态、`0x79198` 解码、`0x78990` 编码。已在隔离的 `/system/bin/sleep` 进程加载原 SO 并调用这三个函数，没有启动原 App，也没有调用 JNI_OnLoad。
3. 解码得到 `dexSize 124284140 sign a02d8f41ad34f11dd843c8fce85e770e`；重新编码结果与原 88 字符载荷逐字相同。
4. `124284140` 恰为 15 个 DEX 未压缩长度之和。完整重建或修改 DEX 后该值需要重新核实，不能只修改 Java 代码就认为打包完成。
5. 配置 sign 的公式已从原证书复算匹配：`MD5(MD5(证书 DER 的小写十六进制 ASCII) + "." + 包名)`。本地测试证书所得值与原配置不同。这里内层 MD5 不是直接对 DER 字节求 MD5。
6. `0xe6bc` 通过 JAR entry 的 `getCertificates/getEncoded` 读证书；另一来源通过 PackageManager 的 `Signature.toCharsString`。另有检查 PackageManager 内部 `mPM` 代理的独立逻辑。
7. 工作线程的失败分支可将全局 `0x9e2e0` 置负；`xKW` 入口读取负标志，静态分支经 `0x174cc → libc exit(0)`。这是一条可解释 Java 退出日志未命中的 native 路径；尚不能将每次退出都归到同一分支。

`0x6c510` 在独立进程对 `abc` 返回标准 MD5 值 `900150983cd24fb0d6963f7d28e17f72`，与静态公式互证。配置编码算法本轮未命名，不应因有 16 字节块和填充就直接称为 AES。

证据：[反汇编与常量解码](evidence/native-integrity-review.txt)、[原始配置编码回环](evidence/integrity-config-result.txt)、[原包和测试证书复算](evidence/integrity-formula-comparison.json)。

**第一份 PNG 更新实验存在构造错误，不能据其失败否定配置修复。** 诊断脚本最初按标准 PNG 重算 tEXt 的 CRC，但原 App 把这四字节用作密文长度。随后冷启动追踪捕获 `0x111bc → NULL`、外层 `0xd5c0 → -17`，并未进入 DEX 大小比较。这是该诊断包的新问题，不应当描述成已经证明原版 DEX 校验失败。

静态读取过程已还原：取资源流总长 N，跳到 N−16，读取 big-endian 长度 L，再 reset 后跳到 N−16−L 并读 L 字节。原图 N=825、L=88，正文起点恰为 721。因此修改后必须保存这项自定义约定。构建脚本已修正，后续运行结果另行记录。证据：[NULL 返回追踪](evidence/combined-integrity-cold-trace.txt)、[读取算法反汇编](evidence/native-integrity-review.txt)、[修正后的构建脚本](work/build_config_probe.py)。

### liblogin_encrypt.so：登录字段 RSA 与签名摘要

已定位 3 个静态导出 JNI 入口：

| 入口 | 作用与证据 |
|---|---|
| `eXYTbsvYIn`，VA `0x8118` | helper 实际经 Java Cipher 调用 `RSA/ECB/PKCS1Padding`，使用 X509EncodedKeySpec 公钥。不是从库名推断。 |
| `AFlIEghJkK`，VA `0x3a18` | 处理 Java TreeMap 排序拼接后的参数；有 SHA-1、Context 包名和产品配置分支。 |
| `bhnYuNkAtG`，VA `0x8324` | Map 排序/拼接及 SHA-1 相关入口；本轮未找到其 loginservice 业务调用方。 |

**离线实测：** 在自己的包名、自己的签名、没有 INTERNET 权限的最小测试 APK 中，仅带此 SO 及准确 JNI 类名，对无个人信息字符串调用字段转换。结果非空，Base64 解码后 128 字节，同一输入两次输出不同，符合随机填充特征。没有输入真实手机号或密码，没有发送任何登录请求。该结果证明字段转换可独立调用，不能替代 signature 或登录成功验证。

库的 ELF 直接依赖只有系统库，没有 `libencrypt.so`。但 AFl 会读取包名，换包名可能选择不同产品参数；`drawable/x_o.png` 的引用在 APK 中没有对应成员，回退逻辑尚未完全还原。因此不能承诺直接复制本库便能保留全部官方登录。

证据：[登录库详细记录](evidence/login-native-review.md)、[独立 JNI 测试结果](evidence/native-offline-jni-result.txt)。登录库记录中的“本轮无模拟器执行”描述其静态子任务；随后主验证已补充上述字段转换测试，实际登录仍未测试。

### liblive_encrypt.so：IM 入房签名和按包名取得 key

三个 JNI 导出可直接定位：`ZUvHJclkKo@0xcdc`、`zupQAsBiNy@0xefc`、`eXqddjLAsE@0x1130`。Java wrapper 分别命名为 getSignKeyNative、getCourseKeyNative 和 getAsrTokenNative。

- IM 入房：`liveim/lib/e/c.java:35` 将房间、用户、设备等构造后的字符串交给 getSignKeyNative，结果进入 RoomJoinReq.signKey。因此它不是广告库。`ZUv` 中 `0xe70` 实际调用 MD5_32。
- 播放地址：`LivePlayUrlUtil.java:27` 把实际 Context 包名传给 getCourseKeyNative，再配合主 EncryptUtil 处理地址解密。两库有 Java 层业务协作，即使没有 ELF 的直接互相链接也不能视为完全独立。
- 离线实测：签名对同一合成字符串稳定、长度 32。Course/ASR 入口对传入 `com.ximalaya.ting.android` 返回非空 32 字符；对测试包名返回 null。

这里验证的是函数**传入的包名字符串分支**，没有证明它检查了实际安装包签名，也没有把返回值输出成可用业务凭据。不能把这项函数测试写成已成功加入直播间。

### libmediadatacryto.so：本地媒体块转换

4 个 JNI 导出分别为 `initLogistic@0xd88`、`encryptData@0xdd0`、`decryptData@0xec0`、`destroyEncryptCtx@0xfb0`。播放器 `player/b.java:155–179` 在 `.x2m` 分支将文件头部 1024 字节交给此库解密；`.x3m` 另有分支，不能一并推定相同。

离线合成 1024 字节输入，库生成同长度且与输入不同的密文，随后解密恢复原数据，回环通过。这个结果验证调用与成对转换，不涉及真实会员媒体或权益，不证明所有格式均支持。

主库还读 x_m/x_z/x_w/x_s/x_q 等资源。x_m 的一个 chunk 可解出 DNS 缓存、APM、日志、MMKV、growth 等业务配置字段，报告和证据仅保留字段名，不复制具体密钥。其他 PNG 使用不同种子或图像处理路径，不能假定都是完整性配置，也不能全部删掉。相关记录：[脱敏后的配置类型结果](evidence/integrity-all-config-results.txt)。

### 如何复验离线测试

在现有 SDK/Java 环境中：`python3 implementation/work/build_native_probe.py` 构建最小包，再在隔离设备执行 `adb -s emulator-5562 install -r implementation/work/native-probe-build/probe.apk` 和 `adb -s emulator-5562 shell am instrument -w com.shixi.nativeprobe/com.shixi.nativeprobe.Probe`。Manifest 没有网络权限，源码在 `implementation/work/native-probe-src/`。成功输出应包含媒体回环 true、直播确定性 true，以及登录字段 128 字节/随机性 true。

配置解析复验还需要在隔离设备的 native sleep 进程中加载原始 SO，运行 `implementation/work/probe_integrity_config.py`；应与已有原配置回环记录一致。它是离线 helper 验证，不是绕过退出后的业务功能验收。

## 自建 App 应如何实现

### 保持已确认的产品范围

- 保留搜索、专辑/声音、播放、直播、打赏，以及签到/收听等非广告任务。
- 不接入广告 SDK，不显示开屏/信息流/播放广告和自动推广弹窗。
- 隐藏广告任务及其引导；不将广告任务伪装成已完成。
- 保留用户主动操作所需的登录、礼物选择、支付确认和错误提示。
- 不通过裁剪改变服务端购买状态或内容权益；移除增值服务推广入口与取得其内容权限是不同功能。

### 结构建议

自行编写原生 Android 页面、网络适配和媒体播放服务；先完成本地历史与播放队列。不搬入原 APK 的主 Application、模块装载器、RN 容器、广告聚合、推送和全套埋点框架。

业务边界分成内容获取、播放地址解析、账号会话、直播房间、打赏交易和任务六部分，接口状态分别处理。普通播放不等待广告或任务初始化，直播观看不等待礼物目录加载；接口失败时保留当前播放，并呈现错误和重试。

优先验证普通 HTTP 音频和公开直播拉流。只有确定必需的房间类型才引入 RTC/IM；不能用普通 FLV 播放器声称已实现所有直播功能。当前不给 APK 体积承诺，最终体积取决于实际所需的媒体及直播组件。

### 官方登录必须先选清楚能力来源

**路线 A：自己的开放平台应用使用喜马拉雅 OAuth。** 官方文档说明创建移动/网页应用、配置 OAuth 回调并通过 SDK/API 获取 accessToken。它证明存在官方授权机制，尚未证明当前开发者入驻、应用审核和所需权限均可取得。文档属于小雅 OS 接入说明，不能据此宣称完整 Android 第三方客户端权限已开放。

来源：[官方账号体系说明](https://open.xiaoyastar.com/os/docs/overview/account.html)，重点为“喜马拉雅账号模式”。其链接到的开放平台 API/SDK 页面本轮未取得可读正文，授权参数和最新 SDK 行为仍待核实。

OAuth token 应独立保存，不可直接填进原 App 的 Cookie。需要应用机密的交换流程应在受控服务端完成；具体采用官方 SDK 还是服务端交换，要依实际接入文档确定，不能把机密常量放进 APK 就视为安全接入。

**路线 B：适配原 App Passport 登录。** 原包使用 nonce、手机号/密码转换、signature、风控材料及服务端颁发的 uid/token。`loginservice/LoginEncryptUtil.java:10–17,31–51` 显示 native `login_encrypt` 边界；会话还涉及 Cookie、Xuid 和 ticket。把界面重新写一遍不会免除这些协议依赖。

如果用户要求“与原 App 同一套账户权益、打赏与任务”，必须分别验证路线 A 的权限是否覆盖；不覆盖则需要路线 B 的真实可行性证据。目前不能承诺这两套会话互通。当前仍遵守不测试登录的范围，不发送验证码，不要求导出用户 token。

### 各核心功能的验证关卡

| 功能 | 已有证据 | 新 App 必须验证 |
|---|---|---|
| 搜索/专辑 | 原版匿名运行成功；静态报告已定位接口 | 独立包发出请求并解析真实响应、分页、空结果和错误 |
| 免费音频 | 原版匿名播放成功 | 新包取得可用媒体地址，连播、暂停/恢复、拖动、切后台及进程恢复 |
| 公开直播 | `live/hall/entity/PgcRoomDetail.java:295–298` 返回首条 FLV；仅证明该房间模型 | 独立包取得房间详情、播放、换房、断线重连、已结束状态；覆盖实际需要的流类型 |
| 打赏 | `LiveGiftSender.java:178–198` 组 gift/room 参数并经 `ap.c(map)` 签名；`host/util/ap.java:18–32` 最终依赖 EncryptUtil | 登录、礼物目录、余额/订单、请求签名、重复提交控制、服务端最终结果；当前不做真实交易测试 |
| 非广告任务 | 同一组件混合收听和广告任务，如 `SevenVideoTaskView.java:114–116,330–339` | 根据任务实际业务类型白名单展示；验证计时/行为上报和服务端认可，不能只做本地倒计时 |
| 官方登录与保持 | 原版 Passport 调用链与 token 轮换已静态定位 | 自有客户端授权、会话恢复、失效、刷新、注销；需后续获准进行账号运行测试 |

播放 BaseInfo 的签名、x-tk 与部分媒体地址 JNI 解密详见原逆向报告；普通播放也不能先假设完全不依赖原 native 库。

### 实施顺序与停止条件

1. **先做无登录技术原型。** 新包、自己的签名、自己的 Application；验证搜索、专辑和免费声音播放全链路。失败必须定位到响应、签名或地址解析，不能用内置 MP3/模拟列表充当接口通过。
2. **验证公开直播。** 在第一关通过后接入实际房间；仅观看，不发礼物。
3. **确认官方登录路径与接口权限。** 先做文档/配置评估。账号测试不属于当前验收；明确可接入后再安排。
4. **再扩展打赏和非广告任务。** 两者均依赖身份和服务端状态，独立于播放验收。

若第一关必须搬入原 App 的全套框架才能运行，应重新评估自建是否还有精简收益。若官方授权不能覆盖打赏/任务，则完整需求仍然未实现；不能把这些功能删掉后称为已经满足。

当前决策：重签启动与匿名播放问题已通过SO配置修正解决，继续验证上述原包精简候选。自建仅是备选方案，未实施；若后续必须进一步大幅缩小体积，再以独立包匿名播放能否跑通作为首个验证关卡。
